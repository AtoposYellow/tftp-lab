[Heading 2] 遇到的问题及解决方法
[Normal Indent] 在服务器的开发过程中，经过详尽的学习、分析与设计，整体编程与调试较为顺利。然而，期间我遇到了一个较为棘手的问题。
[Normal Indent] 在设计多线程逻辑时，最初我没有将每个TFTP会话线程设置为守护线程，这导致了一个严重的潜在问题：当在TFTP客户端强制中断传输（例如在tftpd64中执行break或直接通过任务管理器结束进程）时，由于TFTP会话未正常结束，且早期我设计的upload()方法未设置严格的重传机制，也未使用Python的try...except持续监测timeout事件，服务器将持续等待，使该TFTPSession会话变为无法退出的僵尸线程，最终只能通过任务管理器强制结束程序。
[Normal Indent] 为解决此问题，我通过互联网及DeepSeek认真学习了Python threading库的使用细节，了解到session_thread.daemon = True这一关键语句。通过将每个会话线程定义为守护线程，并根据TFTP RFC规范重新优化了download()和upload()方法，确保了即使在会话出现严重错误无法恢复时，线程也能自动结束其生命周期，从而保证了服务器的稳定性。
[Heading 2] 设计方案存在的不足与改进方案
[Normal Indent] 本服务器主要存在以下两个设计上的不足。
[Heading 3] 块号回滚机制
[Normal Indent] 首先，服务器不支持传输32MB以上的大文件。经与老师交流，这最初源于TFTP RFC规范的限制（块号仅2字节，最大值为65535）。但在后续优化后的RFC规范中，新增了块号回滚机制，即块号达到65535后重新从0开始，从而突破了TFTP传输的文件大小限制。
[Normal Indent] 在传统的TFTP客户端（如Windows命令提示符的TFTP Client）仍遵循经典TFTP RFC规范。如图3-16所示，尝试发送一个192MB的测试压缩包文件test.rar至服务器时，会提示文件无法正常读取。
[Normal Indent] 图3-16 经典TFTP客户端不支持传输32MB以上的大文件
[Normal Indent] 但若使用已更新回滚机制的TFTP客户端程序（如tftpd64），再将test.rar文件发送至服务器，如图3-17所示，查看日志会发现出现了严重的逻辑错误。在接收到块号为65535的DATA包后，按照代码逻辑，服务器期待接收块号为self.block_number++（即65536）的DATA包。然而，此时tftpd64已将块号回滚，从0号开始重新发送数据包，导致TFTP服务器一直认为“收到了重复的数据块”，使得传输无法继续。
[Normal Indent] 图3-17 客户端块号回滚导致服务器持续误判为收到重复包
[Normal Indent] 为解决此问题，只需在upload()和download()方法中重新定义块号的更新逻辑，将所有块号更新定义为模65536的运算。这样，块号形成了一个“环”，从而实现了块号回滚机制。
[Normal] if current_packet_received:  # 当前数据包已接收
[Normal] self.block_number = (self.block_number + 1) % 65536
[Normal] # 更新块号，模65536的运算
[Normal Indent] 代码更新后，重启服务器并重新发送该压缩包文件。如图3-18、3-19和3-20所示，服务器成功实现了块号回滚以支持大文件传输，并能正确计算吞吐量。
[Normal Indent] 图3-18 更新块号回滚机制后服务器对回滚包的正确处理
[Normal Indent] 图3-19 tftpd64成功向TFTP服务器发送192MB大文件
[Normal Indent] 图3-20 TFTP服务器正确计算传输大文件时的吞吐量
[Heading 3] 内存使用开销
[Normal Indent] 当前服务器程序在download()方法中采用了一次性将整个文件读入内存的策略：
[Normal] with open(self.filename, file_mode) as file:
[Normal] if self.mode == 'netascii':
[Normal] data = file.read().encode('ascii')  # 转换为netascii格式并编码为字节
[Normal] else:
[Normal] data = file.read()  # 直接读取二进制数据
[Normal Indent] 此设计虽简便且能减少频繁的磁盘访问，但存在明显局限性：传输大文件时，内存开销与文件大小成正比，存在严重的性能缺陷。作为优化方向，可以避免使用read()方法一次性读取全部内容，转而采用流式读取与发送策略，即每次仅读取和传输一个不超过512字节的数据块。这将内存占用从O(n)降至O(1)，从而支持任意大小的文件传输。
[Normal] with open(self.filename, file_mode) as file:
[Normal] while True:
[Normal] # 获取当前数据块
[Normal] if self.mode == 'netascii':
[Normal] block = file.read(512).encode('ascii')
[Normal] # 转换为netascii格式并编码为字节
[Normal] else:
[Normal] block = file.read(512)  # 直接读取二进制数据
[Normal] if not block:
[Normal] # 发送完毕
[Normal] break
[Normal] current_block_size = len(block)
[Normal] # 发送当前数据包
